# Web (TeaVM)

Runs the Swing/AWT apps in a browser. [TeaVM](https://teavm.org) 0.16.0 compiles the unmodified app sources to JavaScript, and a small AWT/Swing/MIDI compatibility layer ("the shim") stands in for `java.awt`, `javax.swing`, `javax.sound.midi` and the microphone part of `javax.sound.sampled`.

## Build and serve

Requires a JDK (17 or newer) and Maven 3.9. From the repo root:

```powershell
mvn -f web/pom.xml package                          # builds web/target/site
python -m http.server 8000 --directory web/target/site
```

Then open http://localhost:8000/. The site is fully static, so any static file server works. `web/target/` is git-ignored.

To build another checkout of the app sources (for example a branch checked out elsewhere), point `repo.dir` at it and pick an output folder:

```powershell
mvn -f web/pom.xml package "-Drepo.dir=C:/path/to/other/checkout" "-Dsite.dir=C:/path/to/site"
```

### GitHub Pages

The site only uses relative addresses (pages find `boot.js`, each other, the service worker and its scope relative to where they are served), so it works from a sub-path such as https://nate314.github.io/old-java-applications/ as well as from a server root. To build it for Pages locally, pass the Pages address as `site.url`, so the link preview tags (`og:url`, `og:image`) become absolute:

```powershell
mvn -f web/pom.xml package "-Dsite.url=https://nate314.github.io/old-java-applications"
```

To try a sub-path locally, serve a folder that holds `web/target/site` under the name `old-java-applications` (a copy, or a directory junction made with `New-Item -ItemType Junction`) and open http://localhost:8000/old-java-applications/.

`.github/workflows/pages.yml` does this on GitHub: on every push to `master` (and by hand from the Actions tab, `workflow_dispatch`) it checks out the full history (`fetch-depth: 0`, which the Then versions need), sets up JDK 21 (Temurin) and Maven 3.9.9, runs the build above, and publishes `web/target/site` with the official `actions/configure-pages`, `actions/upload-pages-artifact` and `actions/deploy-pages` actions.

One-time setup, in the repository on GitHub: Settings > Pages > Build and deployment > Source: **GitHub Actions**. Until that is set the workflow's deploy step fails. Pushing to `master` (or running the workflow by hand) then publishes the site.

## How it works

### Class substitution

The shim lives in `shim/src/main/java/web/shim/`, mirroring the JDK package names with a `T` prefix: `web.shim.java.awt.TColor` is compiled wherever bytecode refers to `java.awt.Color`. TeaVM 0.16 configures this with a `SubstitutionPolicy` service (`web.teavm.ShimSubstitutionPolicy`, registered in `META-INF/services`). The older `META-INF/teavm.properties` keys (`mapPackageHierarchy`, `stripPrefixFromPackageHierarchyClasses`) no longer exist in 0.16.

Two consequences:

- Rules are tried in classpath order, and teavm-classlib has its own small `Color`, `Dimension` and `Point`. The shim jar must come before teavm-classlib in each app module's dependencies.
- TeaVM renames references only inside substitute classes. A shim helper that mentions a `T` class must itself be a substitute (they live in `web.shim.java.awt.web`, e.g. `TDesktop`, standing in for a made-up `java.awt.web.Desktop`). Helpers in `web.rt` (`Js`, `Edt`, `Exit`, `Sleep`, `Net`, `Files`, `Keys`) never mention shim types.

Also substituted: `javax.sound.sampled` (the microphone, see Images, files and sound), `java.beans.PropertyVetoException`, `java.net.URLClassLoader` (looks classes up among those compiled into the page) and `java.util.jar.JarFile`/`Manifest`/`Attributes` (TeaVM's JarFile cannot read from its in-memory file system).

### Compile-time rewrites

`web.teavm.ShimPlugin` rewrites a few JDK calls in app bytecode only, so app sources stay untouched:

- `Thread.sleep` goes to `web.rt.Sleep`, which throws for negative values like the JDK. Minesweeper's sound helper only stops looping because of that exception.
- `System.exit` goes to `web.rt.Exit`, which closes the app's windows, shows a "Run again" box (with suggestions of other apps, see App pages) and unwinds the calling thread. `boot.js` passes TeaVM's `main` a callback that drops that unwinding, so a program that exits from `main` itself (Windows) is not reported as an uncaught error.
- `URL.openStream` and `URLConnection.getInputStream` go to `web.rt.Net`, which throws `IOException` when a request fails. TeaVM's XHR connection otherwise returns an empty response.
- `Class.getResource` goes to `web.rt.Net.resource`, which returns null: TeaVM has no `getResource`, and the page has no class path to look in. BibleDownloader checks for null and skips its window icon. `Toolkit.getImage(URL)` exists so such code compiles.

### Windows and widgets

Every component owns an absolutely positioned DOM element; Java keeps the real state (bounds, colors, text) because apps compare colors and strings by identity. Layout is done in Java by the shim's `FlowLayout`, `BorderLayout`, `SpringLayout` and null layout, the same way Swing does it, with preferred sizes measured using the same CSS font the DOM uses.

- `JFrame` and `JInternalFrame` are boxes with a title bar (drag to move, close button runs the default close operation). Insets are 28 px on top and 4 px elsewhere, close to Swing's decorations, since apps size their content from the window size.
- `JButton`, `JTextField`, `JComboBox` and `JLabel` are real `<button>`, `<input>`, `<select>` and `<div>` elements. A button with `setBorderPainted(false)` loses the skin's border even when that is called before it is shown. A label whose text starts with `<html>` is rendered as HTML, as in Swing, and measured in a hidden element.
- `JTabbedPane` draws its tabs as DOM buttons and hides the components of the other tabs, as Swing does. `UIManager.setLookAndFeel` does nothing; the page skin is the look and feel.
- `Graphics2D.draw(Shape)` and `fill(Shape)` accept only `Rectangle`, the one shape an app uses.
- Custom painting (`paint`, `paintComponent`) goes to a `<canvas>` inside the component, created the first time `paint` draws, through a `Graphics2D` over `CanvasRenderingContext2D`. The backing store is scaled by `devicePixelRatio`. A `JFrame.paint` override draws over the window's content, as in Swing.
- Components are stacked with `z-index` so the first child is on top, as in AWT.
- The page desktop is the `#desktop` element, and its size is what `Toolkit.getScreenSize()` returns: the whole viewport in the home page's player, and the stage between the toolbar and the controller on an app page (see App pages). A window placed above or left of the desktop's edge is drawn at the edge, so its title bar stays reachable.
- `boot.js` centers the windows, as a group, on the desktop, and scales the desktop down (a CSS transform) when they are bigger than it, or up when they are much smaller and Fit is on (see App pages). A page with `<body data-own-layout>` (CircleSpawner) opts out and keeps the positions the app gives its windows. The scale is `window.__shimScale`, and the shim divides mouse positions and window drags by it, so clicks land on the same pixel as unscaled.

### Events and threads

TeaVM runs Java threads as green threads on the JavaScript event loop. DOM event handlers cannot block, so they only queue work for the shim's event dispatch thread (`web.rt.Edt`), which runs listeners, timers and paint passes one at a time, like Swing's EDT. Listener code there may call `Thread.sleep`.

- Repaints are coalesced into one paint pass per animation frame (with a timer fallback for hidden tabs). A thread other than the EDT that calls `repaint()` waits for that pass, so loops like FlappyBird's `while (true) panel.repaint();` run once per frame instead of hanging the tab.
- `javax.swing.Timer` runs on `setTimeout`; `SwingUtilities.invokeLater` and `EventQueue.invokeLater` queue on the EDT.
- Mouse events go to the deepest component with mouse listeners; key events go through `KeyboardFocusManager` dispatchers, then to the focus owner (the first focusable widget of the active window, or the window itself) as it is when the key's turn on the EDT comes, as in Swing, so a key that moves the focus sends the next one to the new owner. DOM key codes are mapped to AWT `VK_` codes. Tab and Shift+Tab move the focus instead (see Keyboard and screen readers).
- Touch and pens work the apps too (see Touch).
- `java.awt.Robot` can only reach the page: `keyPress`/`keyRelease` queue key events for the focused component, and `getPixelColor` samples the canvas or widget color at that viewport point.

### Standard output

`boot.js` defines `$rt_putStdoutCustom` before `classes.js` loads, so TeaVM hands it `System.out` text. Every page logs it to the browser console line by line. A page with `<body data-console>` would also show it in a panel docked at the bottom of the page; no page uses that now, since GroupCreator and SimpleAlgorithms show their results in their own windows.

### Images, files and sound

- Each app page lists the files it needs in `<body data-files>`. `boot.js` fetches them before `main()` runs; images are decoded so their sizes are known, and every file is copied into TeaVM's in-memory file system so `java.io` finds it by the original relative path. Files the app writes are kept across page loads (see Saved files).
- A `BufferedImage` is a canvas at 1:1 pixels. `getRGB(x, y)` reads one pixel back from it (DinoGame's bot reads the frame it draws each step this way); `getRaster().setPixel` writes.
- Image lookups also match case-insensitively, like the Windows file system the apps were written on (NathaNOS asks for `assets/Clock.png`; the file is `clock.png`).
- `Image.getScaledInstance` is asynchronous in AWT: the first draw of a scaled image draws nothing. The shim keeps that, since FlappyBird's start check waits for that first, still-black frame.
- The system clipboard (`Toolkit.getSystemClipboard`, `StringSelection`) takes text only and cannot be read back: `setContents` writes with `navigator.clipboard.writeText`, or a hidden text area and the copy command where that is refused. Browsers allow it soon after a click or key press, which is when the apps copy (Ultimate Tic-Tac-Toe's Friend by link).
- `javax.sound.midi` is a 16-channel synthesizer on the Web Audio API: one oscillator per note with an attack and release, the waveform picked by the General MIDI program family, and pitch bend as detune. Browsers start audio only after a click or key press.
- `javax.sound.sampled` has only what recording from the microphone needs: `AudioSystem.getTargetDataLine` returns a 16-bit mono line on the page's microphone. `open` asks for it with `getUserMedia` (echo cancellation on, noise suppression off, since it can swallow a held note) and waits, with `Thread.sleep`, for the visitor's answer; a refusal or a missing microphone throws `LineUnavailableException` with a short reason. `read` waits for the sound, which a script node in `boot.js` (`window.__shimMic`) queues (the last two seconds at most). The line's rate is the page's audio rate (usually 48000 Hz), whatever rate was asked for, so apps read it back with `getFormat()`. The line closes itself when the app exits. Call `open` and `read` off the event thread, as on the desktop.
- `Graphics.drawArc` draws an outline arc, as in AWT (angles counterclockwise from 3 o'clock); `fillArc` is not there.

### Saved files

TeaVM's file system lives in memory, so on its own everything an app saves is gone on the next page load. `web.rt.Saves` keeps it, with no change to the apps:

- Every second, and when the page is hidden or closed, it walks the in-memory file system and copies each file written since the last look (TeaVM updates a file's last-modified time on every write) into `localStorage` under `oldjava.saves.<App>` (the page's `data-app`), as a JSON object of absolute path to contents, one character per byte. A file the app deletes is dropped.
- On the next load, right after the page's own files are copied in (`Files.install`, when the first component is created), the saved files are written back over them. So FlappyBird's best score (`/.flappybird-highscore.txt`: `user.home` is `/` here) and today's best run (`/.flappybird-today.txt`), Minesweeper's best times and last level (`/.minesweeper-best.txt`), Ultimate Tic-Tac-Toe's record against the computer and last mode (`/.ultimatetictactoe-record.txt`), TankGame's matches won and lost against the computer (`/.tankgame-record.txt`), SynthesizerKeyboard's best stars per song (`/.synthesizer-songs.txt`) and last tune (`/.synthesizer-tune.txt`) and its looper's loop, tempo, click and mutes (`/.synthesizer-loop.txt`), RubiksCube2D's best stars and moves per level and last level (`/.rubikscube-levels.txt`), MusicTheoryExpert's best score per ear training drill (`/.musictheory-drills.txt`) and its Songwriter song (`/.musictheory-songwriter.txt`), NumberGuess's fewest guesses per range and its duels won, lost and drawn (`/.numberguess-record.txt`), SpriteFloatyStars's most time left per Star Catcher night (`/.spritefloatystars-nights.txt`), GroupCreator's class, rounds and wheel picks (`/.groupcreator-class.txt`), Clock's tab, face, timer, stopwatch, focus session and two weeks of focused minutes (`/.clock.txt`), ScreenSaver's saver, cycling, speed and tile size (`/.screensaver.txt`), StockChecker's edited `myStocks.txt` and its trading desk (`/.stockchecker-desk.txt`), BibleDownloader's place, chapters read, highlights and reading plan (`/.bibledownloader.txt`), and DinoGame's best runs, bot marker and evolved bots (`/.dinogame.txt`) come back as they would from a desktop disk.
- Code that reads a saved file before the app creates its first component sees the page's own copy. Minesweeper, Ultimate Tic-Tac-Toe and SynthesizerKeyboard read their files after `JFrame`'s constructor for that reason.
- The app's own page and the home page's player (`<App>/index.html?embed`) share one store. NathaNOS has its own, so an app opened inside NathaNOS keeps separate saves.
- The title screen reads the store: FlappyBird shows "Your best: N pipes; today's course: N" (the second part only on the day it was flown), Minesweeper "Your best times: Beginner 0:53.6, ...", Ultimate Tic-Tac-Toe "Your record vs the computer: Easy 3 wins, 1 loss, 0 draws; ...", TankGame "Your matches vs the computer: 2 wins, 1 loss", SynthesizerKeyboard "Your songs: Ode to Joy 3 stars, ...", MusicTheoryExpert "Your ear training: 2 of 6 drills passed, 4 of 18 stars", NumberGuess "Your ranges: 1 of 5 won, 3 of 15 stars; duels vs the computer: 4 won, 2 lost, 1 drawn" (either part alone when the other is missing), SpriteFloatyStars "Your Star Catcher nights: 2 of 6 caught, 5 of 18 stars", GroupCreator "Your class: 12 names, 3 rounds of groups remembered, 4 of 12 picked by the wheel" (either part alone when the other is missing), Clock "Your clock: timer running, 19:34 left, 3 laps on the stopwatch, focusing, 18 min left, 2 focus sessions today" (or "your timer has rung", or the length of the timer that is set), NathaNOS "Your desktop: Sunset hills wallpaper, icons arranged by hand", ScreenSaver "Your screen saver: Pipes, then the next every 30 s" (or "kept on screen"), StockChecker "Your trading desk: day 4, closed day 3 at $10,871 (+8.7% since day 1), ahead of 2 of 4 rivals", BibleDownloader "Your Bible: open at Luke 1:14, 3 of 1,189 chapters read, 1 highlight; reading plan: The Gospels in 30 days, day 5 of 30, 9 of 89 chapters" (the plan part only while one is followed), DinoGame "Your best: 23; the bot's best: 491; your evolved bots: 3000 after 40 generations" (or "No run of your own yet" before your first), and any other app with saves names the files ("Saved here from last time: myStocks.txt"). Forget on that line (click twice) deletes the app's saves, so it starts again from its bundled files. The formats are the `RECORDS` table in `boot.js`.
- Files written under `~/Downloads` (`/Downloads/`) are not kept. Each is handed to the browser as a download (a Blob and an `<a download>` click, `Js.download`) and then deleted from the in-memory file system. BibleDownloader saves its chapters there, so on the web Save downloads `Luke.html` as a browser would.
- A full `localStorage` logs an error and keeps the previous copy. Thumbnail mode (`?embed&shot`) is not special-cased, so take thumbnails in a fresh browser profile (as `shots.ps1` does).

### NathaNOS and reflection

NathaNOS loads the `Main-Class` of each jar in `assets/` with `URLClassLoader`, then calls its `(Boolean)` constructor or its `main` method by reflection. In the browser nothing can be loaded at run time, so the `nathanos` module compiles `assets/Clock.jar` and the other browser apps' sources in with NathaNOS:

- Its entry point, `web.nathanos.Boot`, registers each app's main class in `web.rt.Classes` and then starts NathaNOS. That makes TeaVM compile the classes, and lets the shim's `URLClassLoader` find them by name. TeaVM's own `Class.forName` only finds classes the program creates instances of, which leaves out most apps' `Main` (just a static `main`).
- `web.teavm.ShimReflectionPolicy` keeps the constructors and `main` method of every app class that declares a `main`.
- Each app gets a jar in `assets/` holding only a manifest that names its `Main-Class` (built with Ant's `jar` task), since NathaNOS lists jars to build its desktop icons and start menu and reads only their manifests. The page preloads those jars, plus FlappyBird's images and StockChecker's files.
- NathaNOS's desktop window is not focusable, so `TDesktop` does not raise it when it is clicked, and apps stay in front. It also switches every app window to `DISPOSE_ON_CLOSE` through `Toolkit.addAWTEventListener` (`WINDOW_OPENED`), so closing an app does not run `System.exit`.

Adding an app takes its sources and a jar entry in `nathanos/pom.xml`, a line in `Boot`, and its jar and files in `data-files` in `site/NathaNOS/index.html`.

## Layout

- `pom.xml`: parent build (TeaVM version, shared plugin settings).
- `shim/`: the compatibility layer and the TeaVM compiler extensions (`web.teavm`).
- `apps/`: compiles every app except NathaNOS straight from `<App>/src`, one TeaVM run per app, and copies the static site and app files, plus every browser app's README and Java sources (NathaNOS included) into `<App>/source/` for the source viewer, and writes `history.txt` from the repo's git log (see What's new).
- `then/`: 16 apps as they were first restored (see Then and now), each compiled to `<App>/then.js` with its page `<App>/then.html` (from the one template `then/then.html`) and its sources in `<App>/then-source/`.
- `then-nathanos/`: NathaNOS as first restored, the same way, with that commit's apps and `assets/Clock.jar`.
- `nathanos/`: NathaNOS plus `assets/Clock.jar` and the other browser apps, in one page (Clock.jar's `clock.Main` clashes with the Clock app's, so the Clock sources are left out).
- `site/`: `index.html`, one `<App>/index.html` per app, `boot.js`, `news.js` (What's new), `clockbar.js` (Clock follows you), `shim.css` (the Modern, Classic and Arcade skins), `shots/` (the home page thumbnails), `clips/` (the gallery's preview clips), `cards/` (the link preview cards, see Share), and `sw.js`, `manifest.webmanifest` and `icons/` (install and offline).
- `shots.ps1`: recaptures `site/shots/` from a built site, following a recipe per app (see Home page).
- `clips.ps1`: records `site/clips/` from a built site (see Home page).
- `cdp.ps1`: what those two share: the site's server, headless Chrome and a small DevTools protocol client that loads an app page and plays a recipe's steps (keys, clicks, page scripts, waits).
- `cards.ps1` and `card.html`: render `site/cards/` and write the share tags into every page (see Share).

## Home page

The home page opens with a player: Minesweeper is already running in it, and every card's Play button (or thumbnail) swaps that app into the player without leaving the page. Full page opens the app's own page, as do Ctrl-, Shift- and middle-clicks on Play. Selecting an app puts it in the address (`index.html#FlappyBird`), and loading that address starts the page with that app in the player. The filter buttons narrow the cards to games, music, toys or tools.

The player is built to keep a visitor playing without scrolling back to the gallery:

- A rail of thumbnails under the screen lists all 20 apps; clicking one swaps it in. The current app is outlined and the rail scrolls to keep it in view. The arrows at either end play the previous or next app (wrapping around), and Shuffle plays a random app other than the current one.
- Big screen fills the monitor with the player (bar, screen and rail) through the Fullscreen API, where the screen gets all the room the bar and the rail leave. Where the browser refuses fullscreen (inside an iframe without `allowfullscreen`, for example), the player covers the browser window instead, and the button (or Esc, while the page rather than the app has focus) leaves it.

- The player is an iframe of `<App>/index.html?embed`. In embed mode `boot.js` leaves out the toolbar and keeps the app's windows centered as a group (scaled down if they do not fit), since most apps open their window at the top-left corner of the screen. It recenters only when a window opens, closes or changes size, or the viewport does, so dragging a window or moving it with the arrow keys (Minesweeper) works as usual.
- The iframe's viewport is at least 900 x 520 (720 tall for Rubik's Cube, whose window is 700 px tall) and is scaled down to the width of the page. The player is never taller than the browser window minus room for its bar and rail.
- Under the player, Your arcade is one panel with four tabs: What's new, Passport, Records and Take it with you (each described in its own section below). Before, they were four panels one after another, so the gallery started about 1,200 px below the player (at 1920 x 855, 2,251 px down the page); now it starts after one panel (1,470 px down, and the page is about 800 px shorter). Badges name each tab's news: New when an app you played has changed, your stamps (3/20), the number of apps with saves. A Send to my phone link (`?saves=`) opens the Records tab before it asks.
- Pocket player. On pages up to 640 px wide (phones) that scaling made every app a postage stamp: a screen 341 px wide (on a page 390 px wide) showed the 900 px viewport at a third of its size, 16:10 and about 210 px tall, so Minesweeper's tiles were 7 px wide. The lead above the player drops its sentence about TeaVM, and the rail's thumbnails get smaller. ## App pages

Each app page (`<App>/index.html`) is built to lead to the next app as well as run its own:

- The page is a stage. The toolbar is a band across the top: the app's name on the left, with a light that is amber on the title screen and green once the app runs, and on the right a ? button (How to play, see below), All apps, Switch app, Source (see Source viewer), Share (see Share), a Next link (the following app in gallery order, wrapping around; hidden on pages narrower than 560 px), Fit (see below), Pop out (see Pop out) and the skin picker. On narrow pages the band wraps to a second row. Each skin draws it: dark glass in Modern, a steel blue bar in Classic, a neon-edged bar with a cyan name in Arcade.
- The app's desktop is the space left between the band and the touch controller (when it shows) at the bottom. The shim reports that space as the screen, so apps that size or center their windows from the screen fit it, and `boot.js` keeps the windows centered on it, scaled down when they are still bigger (Rubik's Cube on a short page, TankGame above its controller). No window sits under the toolbar or the controller at any page size, and the stage follows them as they change height (the band wrapping, Controls toggling the controller, the output panel growing). On pages wider than 900 px the open Source panel ends the stage at its left edge, so the windows stay in view beside their code. A change in the stage's size alone (the controller toggled, the band wrapping, the Source panel docking, the browser resized) moves and scales the windows with the stage but keeps the centering they last had, so a window the visitor dragged keeps its place beside the others instead of snapping back to the center.
- Fit to screen. Many of these apps open small windows (Dino Game's is 728 x 252, Clock's 480 x 480), which sat small in the middle of a large screen. `boot.js` now also zooms them up: the windows, as a group, are shown at 90% of the largest size that fits the stage, rounded down to a quarter step and at most 2.5 times their size (Dino Game 2.25 times and Number Guess 1.75 times on a 1920 x 815 stage, Clock 1.25 times on a 900 x 600 page). Windows that already fill the stage (FlappyBird, NathaNOS, ScreenSaver, Minesweeper on most screens) stay as they are, and windows still too big are scaled down as before. The toolbar's Fit button (with the zoom it picked, such as `Fit 2.25×`) switches to Actual size and back; the home page's player bar has the same button, so Big screen now makes a small app big as well. The choice is kept in `localStorage` (`oldjava.zoom`) and reaches every open page of the site through the `storage` event. CircleSpawner, Windows and WindowsE place their own windows and have no Fit button.
- The zoom stays sharp. Widgets are HTML, which the browser draws at the zoomed size, and the apps' own drawing goes to canvases that get that many more pixels: `boot.js` sets `window.__shimRender` (devicePixelRatio times the zoom, at most 2.5) and sends a `shimrender` event, and the shim sizes every paint canvas by it and paints every window again. Pictures the apps load (FlappyBird's sprites, for example) are drawn from their own pixels, so they are only as sharp as the file. Clicks, drags and the touch gestures land on the same pixel as at actual size, since the shim divides pointer positions by the scale (`window.__shimScale`) either way.
- A page with `<body data-tab-title>` (Clock) puts its window's title in the browser tab's title whenever it says more than the app's name, so Clock's "4:59 left - Clock" and "Time's up! - Clock" can be watched from another tab. The home page's player leaves the home page's title alone.
- Switch app opens a panel on the right with every app's thumbnail, name and hint, the current app marked "Now playing". Esc, the close button or a click outside the panel closes it.
- Nothing floats over the stage. The band's name slot doubles as a news line (`bandNews` in `boot.js`): when the app starts, the name slides up and "How to play" with the app's hint slides in for 12 seconds, then the name comes back. A hint longer than the slot scrolls through it like a marquee, twice (it stays longer to do so; with reduced motion it is cut off with an ellipsis and the full text is its tooltip). Pointing at the line holds it, and its x or Escape closes it. The ? button shows the hint again, and is lit while it shows. A new passport stamp uses the same line (see Arcade passport). On pages narrower than 560 px the slot and the ? button take the band's first row, so the line has room. Since the band's height never changes for the news, the stage never moves for it either.
- When the app exits (for most apps, when its window is closed), the Run again box names the app, keeps Run again and All apps, and suggests three other apps with their thumbnails: apps not played yet first (see Arcade passport), and within that, apps of the same category first, then the others, each group in random order. The box ends with the passport count. In the home page's player the box has no All apps link, and picking a suggestion asks the home page (with `postMessage`) to swap that app into the player, so its title, rail and address follow.

## Pop out

These were desktop apps, each in a window of its own. Pop out gives them one again: a small window that stays on top of every other window on the screen, the browser's included, so Clock's timer stays in sight over a document, a song plays on the Synthesizer beside an email, or the Dino Game's bot runs in a corner of the screen.

- The toolbar's Pop out button (⧉, after Fit) opens the window with the browser's Document Picture-in-Picture API and moves the page's `#desktop` into it, windows and all (`popOut` and `popInto` in `boot.js`). It is the same running app, not a second copy: a game in progress, a running timer or a selected tile go on where they were. From the title screen, Pop out starts the app straight into the window.
- The window is sized to the app's windows at their actual size, with a 16 px margin (Chrome counts its own title bar in the height asked for, so 56 px are added for it). `centerWindows` keeps working on the moved desktop: the windows stay centered, are scaled down if the window is smaller, and Fit zooms them up when the visitor drags the window bigger.
- The window gets the page's stylesheets and follows the page's skin (a skin change anywhere on the site reaches it). It is styled like the home page's player (`data-embed`): the desk on the page, without the Arcade scanlines.
- The shim follows the desktop. While it is out, `window.__shimDoc` is the small window's document: the shim looks up the desktop, its size (the app's screen), points under the pointer (touch, and DinoGame's bot reading its pixel) and the focus there, and `boot.js` passes the document to `window.__shimListen`, which installs the shim's mouse, touch and key listeners on it (`TDesktop.installListeners`). Keys pressed on the page itself still reach the app too, so the page's touch controller drives a popped out game.
- The page's stage shows a card in its place ("Clock is in its own window", with a floating window drawn above a screen) and a Bring it back button; the toolbar button reads Bring back. Closing the small window, either button, or closing the app's own window (whose exit screen then shows on the page) brings the desktop back into the page, where it is centered again. Popping out stamps the passport, and the site sounds play their open and close notes.
- The home page's player bar has the same button. The player's iframe may not open the window itself (browsers allow it only to a top-level page), so the home page opens it, sized by the app's page (`window.oldjavaPop.size`), and hands it over (`window.oldjavaPop.into`). Swapping another app into the player brings the popped out one back first, which closes its window.
- Windows and WindowsE (whose pretend Windows lives in the page) and CircleSpawner (which places its own windows on the screen it was given) have no Pop out, and neither does a browser without Document Picture-in-Picture: there the button is not shown.

## Instant replay

The moments worth keeping (a run of 30 pipes, a bank shot that wins the round, a tune played right) are over before anyone thinks to press record, and a link to the app does not show them. So every running app keeps its last moments, and Replay turns them into a video to watch, save or share.

- Recording starts when the app does (`startReplay` in `boot.js`) and needs nothing from the app. Up to 30 times a second `drawDesk` draws the app's windows into a canvas of their own: it walks each window's elements in stacking order and paints their backgrounds (plain colors, and the skins' gradients), borders and the windows' inset frames, the apps' paint canvases and pictures, the text of labels and buttons at the places the page lays it out (a range's line boxes), and the values of fields and lists, on the skin's desk with a 16 px margin. Apps with many widgets cost more to draw (Minesweeper's 15 x 15 Classic board took about 8 ms in testing), so they are drawn less often: drawing takes at most a tenth of the page's time.
- Only an app that changed is drawn again. The shim sets `window.__shimPainted` whenever anything draws on a canvas (`Js.painted`, from `TCanvasGraphics` and the canvas clears and resizes), and a `MutationObserver` on the desktop sees the rest (labels and buttons changing, windows opening or moving, a skin change). While neither happens, the app is drawn once a second, so a clip's last frame is never more than a second old, and the recorders' canvas gets no new frames to encode. A still app used to cost as much as a moving one: in a headless Chrome test, 10 seconds of an idle app with the old loop took 55 to 81% of one CPU core across all of Chrome's processes (Minesweeper, Music Theory Expert, Rubik's Cube), and now take 7 to 9%; games that move all the time (FlappyBird, 86 to 89%) cost what they did. Idle clips are smaller too (a 13 second clip of Music Theory Expert at rest is about 84 KB).
- Two `MediaRecorder`s take turns on the canvas's stream: each is restarted every 20 seconds, half a segment apart, so one always holds between 10 and 20 seconds. Replay stops that one, starts a new one in its place, and shows its video. Nothing else is kept, so memory stays at two short videos.
- The clip is the windows' size at up to twice their actual size (at most 1280 px on the longest side), whatever the zoom or the screen. A recording keeps the size it started with (Chrome's MP4 recording does not follow a change of size), so when the windows come out much bigger or smaller (a splash before the app's window, a switch to Minesweeper's Expert board) they are fitted into the old size at first, and after a second at their new size the recording starts over at it.
- The app's sound is recorded too: its MIDI voices now meet in one gain node on their way out (`appOut`), which the recorder listens to, so the site's own sounds stay out of the clip. Microphone input (Sing along) is not recorded.
- MP4 where the browser records it (Chrome does), else WebM. Nothing is drawn or recorded while nobody can see the app: the page is hidden, or it has been scrolled so the app is out of view (an `IntersectionObserver` on the page's body; in the home page's player that is the whole iframe, so scrolling down to the gallery pauses the player's recording; the home page went from about 50% of a core to 11% in the same test, the rest being the player's app itself). The clip's seconds leave out the paused time. An app popped out (see Pop out) keeps recording, from the small window's frames.
- Replay is in the app page's toolbar (a red dot, with the word on pages 1000 px wide or more), shown once the recording has started; on the exit screen ("⟲ Replay", the last moments before the app closed); and in the home page's player bar, shown when the player's app reports that it is recording (`postMessage`), which takes the clip from the iframe (`window.oldjavaReplay.take`) and shows it on the home page at full size. Windows and WindowsE, whose pretend Windows is drawn by the page, have no Replay.
- The panel plays the clip on a loop (with sound, since it opens on a click), says how many seconds it holds, and has Save video (a download named like `FlappyBird-replay-20261102-1655.mp4`) and Share..., where the browser can share files (`navigator.canShare`), which sends the video with the app's link to the system share sheet. The video stays in the page unless the visitor saves or shares it. Keys typed in the panel stay out of the app, and Esc, the close button or a click outside closes it. It uses the Share panel's frame in each skin.
- Limits: drawing the page's elements is an approximation of the browser's own rendering: text shadows, outer box shadows, focus rings, CSS pseudo-elements and images used as CSS backgrounds are left out, and a gradient is drawn top to bottom, left to right or corner to corner from its colors. Tested in Chrome only.

## The site's screen saver

Screen Saver is one of the apps, and it is also the site's own screen saver. A page of the site (the home page or an app page) left without a key press, click, touch, mouse move, wheel turn or controller press for 3 minutes fades Screen Saver in over everything, the way a desktop does after a while away:

- It is the app itself: an iframe of `ScreenSaver/index.html?embed&saver` covering the page (`showSaver` in `boot.js`). Saver mode is like thumbnail mode: no title screen, passport stamp, replay or touch controller. It shares the app's saves, so it shows the saver the visitor left the app on, cycling or kept on screen, at their speed and tile size, and carries on through the list from there. A visitor who picked the Aquarium comes back from a break to their own fish, and a look in on a new day brings a new one.
- The first key press, click, touch, controller press or real mouse move (more than a few pixels, since showing it can send a move from a mouse that has not moved) fades it out. That input never reaches the app beneath: every page, the home page's player and the saver's own frame included, hands its input to the top page first (a capture listener on `window`, before the shim's), which keeps the key and its release from the app, and keeps the saver up until a held button is let go.
- Then the page says what that was ("Welcome back! That was Screen Saver, one of the 20 apps here..."), in the band's news line on an app page and in a toast on the home page, with Pick your saver (Screen Saver's page, or the home page's player) and Turn it off. Off is kept in `localStorage` (`oldjava.saver`) for every page; Screen Saver's title screen says whether it is on and turns it on and off.
- It waits while the page is hidden or in fullscreen, while the computer plays (watch, so the home page's opening demo is never covered), while the app is popped out or a video (a replay) plays, and on the apps that are read or watched without touching them: Screen Saver itself, Bible Downloader and Clock. Its 3 minutes start again when the reason ends.
- `window.oldjavaSaver` has `show()`, `wake()`, `showing()` and `after` (the wait in milliseconds), for testing.

## What's new

The arcade changes often, and nothing on the site used to say so: a visitor who came back saw the same gallery and had no way to know that Flappy Bird now tilts and dives or that the Algorithm Lab opens on a sorting race. The site now tells its own history, built from the repo's git log, so it is always as current as the build and never written by hand:

- At build time the `apps` module runs `git log --no-merges --name-only` and writes `history.txt`: one `@@<commit time> <subject>` line per commit, newest first, each followed by the top-level folders the commit changed (a squash merge's `(#N)` is dropped). A commit belongs to an app when it changed that app's folder. Like Then and now, the build needs `git` and the repo's history.
- `news.js` reads it. On the home page, What's new (a tab of Your arcade, under the player) shows the latest six changes as cards: the app's picture, the date, the subject split at its colon into a headline and a line under it, and Play, which swaps the app into the player. A change to two to four apps has a button per app. A change to no app's folder is marked All apps, and one to more than four apps is marked with their count; neither has a button. Show all lists every change back to the first commit of the recovered apps.
- What changed since you last played. `boot.js` keeps when each app was last played (`oldjava.lastPlayed` in `localStorage`, set whenever the passport stamps a play of today's version; an app played before that counts from its first stamp in `oldjava.played`). Apps the visitor has played that have a change (to four apps or fewer) newer than that are named at the top ("Changed since you last played them: ..."), with a button that plays the newest one; those changes lead the list, outlined and tagged Since you played, and the apps' gallery cards get an Updated tag. Playing one clears it, on every open page (the `storage` event). A change counts from its commit time, not from when it was deployed.
- On an app page the title screen ends with the app's story, a disclosure that names the latest change ("Latest change", or how many came since the visitor last played it) and opens to every change to that app, newest first, with its date. Opening it does not start the app. `boot.js` adds `news.js` to the page only for this; `then.html` pages leave it out.
- `window.oldjavaNews` has `load()` (the parsed history and the catalog), `story(id, element)` and `lastPlayed(id)`.

## Watch the computer play

A visitor who lands on the home page sees an app waiting for a click; a game that is already being played shows what it is in a few seconds. So four games can play themselves, and the home page opens on one doing it.

- The apps: Minesweeper (W) solves its board with `Solver`, which sees only what a player sees: it plays what `Logic` can work out (a count whose mines are all found opens its other neighbors, a count with as many hidden neighbors as mines left flags them, two overlapping counts settle the tiles only one touches, and the mine count), says why under the board with the numbers it read ringed in gold, and with nothing certain it guesses the tile least likely to be a mine. Since boards are now dealt to need no guess (Minesweeper's No guess, on by default), the demo on the home page no longer loses to a coin flip. It moves about three times a second, with the keyboard cursor ring on the tile it plays, and starts a new game a moment after each one ends. In the self-check (on random boards) it won 187 of 200 Beginner games, 199 of 200 Classic and 169 of 200 Expert. Ultimate Tic-Tac-Toe (W) plays both sides with a 150 ms Hard search each. TankGame (C) drives red with a second copy of the computer that drives green, starting matches against itself from the title card. DinoGame (B) is its original bot, as before. The keys work on the desktop too; each app's README has the details.
- None of it counts: Minesweeper records no best time for a board the computer played on, Ultimate Tic-Tac-Toe does not count a game the computer played X in, and TankGame does not record a match the computer drove red in. DinoGame already kept team runs out of both bests.
- `?watch` on one of those four app pages (`WATCH` in `boot.js`, with the app's key) skips the title screen, presses the key once the app's window is on the desktop, mutes the app's voices (the gain node instant replay records from, so a clip of a demo is silent) and shows a line over the stage: a blinking dot, "The computer is playing", "Click or press any key to take over". The four title screens offer "Watch the computer play it first", a link to `?watch`.
- Taking over: the visitor's first real click or key on the page (not on the toolbar or a panel; the touch controller counts) presses the key again, so the computer stops, before the visitor's own press reaches the app. That press is their first move: the click reveals the tile, the Space jumps. The app's sound comes back, the passport stamps the app (it waits for this, not the demo), and `?watch` is dropped from the address, so a reload starts the app for the visitor. Pressing the app's key itself only stops the computer. Each app also stops on its own when played: a click on a Minesweeper tile, or on an Ultimate Tic-Tac-Toe cell or mode button.
- The home page's player starts on `Minesweeper/index.html?embed&watch` when the address names no app. Until the visitor picks an app, restarts, or takes over (the player's page says so with `postMessage`), it swaps in the next of the four every 40 seconds, while the page is visible and the player is in view. A press on the docked controller asks the player's page to take over first (`oldjavaWatchTake`), then passes the press in.
- Limits: a game controller's buttons reach the app as synthetic key presses, so they do not take over; a click does. Ultimate Tic-Tac-Toe's search holds the page for 150 ms per move while it is watched.

## Touch

On a phone or tablet a finger is the left mouse button, so every app can be played by touch, not only the four with a touch controller:

- The mouse still arrives as mouse events. Fingers and pens arrive as pointer events (`TDesktop`'s `onTouch*`), and the mouse events a browser makes up after a tap are ignored for a second after the last touch, so nothing is clicked twice.
- A tap is a press, a release and a click. A drag is a drag: windows move by their title bars, Clock's timer dial turns, and anything else an app drags with the mouse follows the finger. Browsers send no mouse events while a finger moves, so before this none of that worked by touch.
- Two taps within 500 ms and 30 px are a double click (NathaNOS opens its desktop icons on one). A pointer event carries no click count, so the shim counts the taps.
- Holding still for 500 ms on a button that listens to the mouse itself is a right click: the left press ends without a click and a right press, release and click follow. That is Minesweeper's flag (long-press a tile to cycle flag, question mark and blank). A desktop pane gets the same, so a long press on NathaNOS's empty desktop opens its wallpaper menu. A ring closes in on the finger while it is held and pops when the right click goes (with a short vibration where the phone allows it); a quick tap shows nothing. Other buttons and panels keep a long press as a long left press, so held keys and press-and-drag work as before. Clock's right click (12 or 24 hours) has no touch equivalent.
- Windows have `touch-action: none`, so a finger on a window works the app instead of panning or zooming the page; a swipe outside the windows still scrolls the home page. They also turn off the long-press callout and the tap flash.
- Only the first finger counts; a second one is ignored until the first lifts. A touch the browser cancels is released without a click.

## Keyboard and screen readers

The apps can be played without a mouse, and a screen reader can tell what is on them:

- **Tab and Shift+Tab** move the focus through the active window's buttons, fields and lists, top to bottom and left to right, as Swing's focus traversal does (`TDesktop.traverseFocus`), and the page's keyboard focus moves with it, so the focus ring and a screen reader follow. Components an app made unfocusable (Minesweeper's level buttons) get `tabindex="-1"` and are skipped, as in Swing. Space presses the focused button, as in Swing.
- **No keyboard trap.** Before, every key on an app page went to the app, Tab included, so the keyboard could never reach the page's toolbar. Now Tab past the last component (or Shift+Tab before the first) is left to the browser, which moves on to the toolbar or the window's close box, and Enter on the page's own links and buttons works them. Tab from the page itself (nothing focused) goes into the app where its focus is. Focus the browser moves onto an app's button some other way (its own Tab, a screen reader) becomes Swing's focus too.
- **Focus follows the app.** When an app moves the focus (`requestFocus`), a button or field gets the page's keyboard focus; a painted panel takes it off the app's buttons, so Space does not press the button clicked last. A newly opened window's first focus does not take the page's focus, so the home page's player never grabs the keyboard.
- **Names.** A window with a title bar is a `role="dialog"` named by its title. `getAccessibleContext().setAccessibleName` and `setAccessibleDescription`, Swing's own accessibility calls (`javax.accessibility.AccessibleContext`, substituted like `java.awt`), become the element's `aria-label` and `aria-description`. On the desktop the same names reach screen readers through the Java Access Bridge. Minesweeper names every tile ("3 mines near, row 2, column 5", "flag, row 7, column 4", "hidden, ...") and Ultimate Tic-Tac-Toe every square ("empty, open, top left board, middle square", "O, last move, ...").
- **Announcements.** A window title that changes within 1.5 s of a key press or a click is read out through a polite live region (`Js.announce`, a visually hidden `role="status"`): a flag placed ("Minesweeper: 17 mines left"), a mine hit, a win, the computer's reply in Ultimate Tic-Tac-Toe ("X to move"). Titles that change on their own, like Clock's countdown, are not read, so they do not talk over everything.
- The focus ring is a 3 px ring in the skin's `--focus-ring` color with a white edge inside it, so it shows on any color an app paints its buttons. It shows only when the last input was a key: Swing focuses a button that is clicked, and the shim moves the page's focus with it, but asks the browser not to ring it (`focusVisible: false`), so clicking a tile or a button no longer leaves a keyboard ring on it.
- Minesweeper is played entirely from the keyboard: Tab into the board, the arrow keys move a cursor from tile to tile (a blue ring, on the desktop too), Space or Enter reveals, F flags (or the menu key, or Shift+F10), and a new game keeps the cursor where it was. Shift+arrows move the window, which the plain arrows did before.

Checked with Chrome's accessibility tree and real key presses; not yet with NVDA, JAWS or VoiceOver themselves.

## Pretend Windows

Windows and WindowsE were written to drive the real Windows with `java.awt.Robot`, and do nothing else: Windows presses the Windows key once and exits 100 ms later, WindowsE holds the Windows key and taps E as many times as its field says. Their pages (`<body data-shell>`) play the Windows they expect, inside the stage, so their unchanged code has something to press keys on:

- The shim's `TRobot` treats the Windows key (`VK_WINDOWS`, 524) as the operating system's. A key pressed while it is held goes to `window.__shimShell` as a shortcut, not to the app's window; the Windows key alone goes there when it is released with nothing pressed in between, as on Windows.
- `boot.js` (`pretendWindows`) answers the Windows key with a Start menu rising from the bottom of the stage: a search field that has the keyboard, every app on the site as a tile (from the gallery, with a check on played ones), the passport count and a power button that closes the menu. Typing narrows the tiles by name, folder name or hint; Enter plays the best match. Esc, the power button or a click outside closes it.
- Win+E opens a File Explorer window on `This PC > java-applications`: the 20 app folders, each with the app's thumbnail as the paper inside, cascaded 28 px down and right from the last one (starting over at the top left when the next would not fit). Click a folder to see its name and hint in the status bar and an Open button; double-click it (or Enter) to play it. The windows can be dragged by their title bar, come to the front when clicked and close with their x; a tray at the bottom left counts them and has Close all. At most 40 are open at once, so WindowsE's field cannot fill the page forever.
- Windows outlives the program that pressed its keys: when the app exits (Windows does at once), the exit screen waits until the Start menu is closed.
- In the home page's player, a tile or folder swaps that app into the player, like the other app links.
- The menu and the windows take the skin's window colors; Arcade turns the folders magenta.

## Title screen

An app page opens on a title screen instead of a bare "Loading..." box, the way an arcade cabinet shows its attract screen before a game:

## Game controllers

Plug a game controller into the computer (or pair it with the phone), press any button, and it plays every app. Browsers report a controller to a page only after one of its buttons is pressed there, so that first press is when the controller chart appears. It uses the Gamepad API's standard layout (an Xbox or PlayStation style pad); `boot.js` polls it once per animation frame.

- **The chart**: on an app page, the toolbar band's news line shows what each button does in that app (`Controller` A Flap, X Course, ...). On the home page it takes the place of the player's hint for 15 seconds. Back shows it again.

## Skins

The picker in the top-right corner switches between four skins:

- Modern (the default): flatter, rounded, follows the system dark mode.
- Classic: close to Swing's default Metal look.
- Arcade: every app as if on a CRT arcade cabinet. Windows get neon magenta frames with a glow, cyan title text and buttons, and phosphor-green text fields and output panels, on a dark purple desk with a faint grid. Fine scanlines and a vignette cover the page, and a faint bright band rolls down it. When an app starts, its windows open from a bright line like a tube warming up, so every app swapped into the home page's player powers on too. The home page turns into a neon cabinet as well (glowing title, player and buttons).
- Yours: a skin the visitor makes and can send as a link (see [Your skin](#your-skin)).

The home page's player bar has an Arcade mode button that switches every open page of the site to Arcade and back to the skin from before. The choice is remembered in `localStorage` (`oldjava.skin`). Skins only change colors and decoration; sizes and widget fonts come from Java, so the layout is the same in every skin. Colors an app sets itself, and anything it draws (Minesweeper's grass and sand tiles, for example), are kept in every skin.

In Arcade the scanlines and the rolling band are pseudo-elements of the page's `body` that never take pointer events. Pages in the home page's player leave them out (the home page draws them once over the player), and so does thumbnail mode. The power-on animates the CSS `scale` property of `#desktop`, so it does not disturb the `transform` that centers the windows in the player. The rolling band and the power-on are left out when the system asks for reduced motion. The thumbnails stay Modern screenshots in every skin.

### Your skin

A fourth choice in the picker, Yours, is a skin the visitor makes. Choosing it (or Edit beside the picker while it is worn, Your skin in the home page's player bar, or Find's "Make your own skin") opens a panel at the side of the page (a sheet along the bottom on screens up to 560 px wide) with five choices: Light or Dark, a color (ten swatches or any color from the browser's picker), a desk wallpaper (Plain, Fade, Grid, Dots, Stripes, Aurora, each tile drawn in the chosen color), corners (Square, Soft, Round) and windows (Flat, Glossy with a title bar in the color, Glow with a colored halo). Each choice is put on at once on every open page, including the home page's player, so the running app is the preview. Surprise me rolls all five, Undo (or Back to the skin worn before) puts the old one back, and Copy link copies the page's address with `?skin=<code>`.

The five choices are kept as a short code in `localStorage` (`oldjava.ownSkin`, for example `l-7c3aed-aurora-1-gloss`). `boot.js` turns the code into the skin's CSS variables (`ownCss`) in a `<style>` of its own before first paint, so a page never flashes another skin; the color becomes the accent, darkened or lightened until white text on it and the accent as text on the page stay readable, and the wallpaper's second color is the accent with its hue turned. The panel is `skinmaker.js`, added the first time it opens. A page opened with `?skin=<code>` wears that skin at once and saves it, and a box asks to keep it, change it or go back to the skin from before. Keys pressed in the panel never reach the app or the title screen. Like the other skins it only changes colors and decoration, so layouts are the same.

## Your records

What the apps save stays in the browser that saved it (see Saved files), so a best time set on a laptop was missing on the phone, and records kept by the desktop apps (`~/.minesweeper-best.txt` and the rest) never met the ones kept in a browser, although they are the same files. The home page's Your records panel (the Records tab of Your arcade) shows them and carries them:

- It lists every app with saves in this browser, each with its thumbnail and the same record line its title screen shows ("Your best times: Beginner 0:53.6, Classic 3:04.2"; an app without a record line names its files). The line is `boot.js`'s `RECORDS` table, exposed as `window.oldjavaRecords.line(app, files)` so it also reads saves that came from elsewhere. Clicking an entry plays the app in the player. The list follows the player's app as it saves.
- A saves bundle carries them: `{ "oldjava": "saves", "v": 1, "at": ..., "saves": { "<App>": { "/.file.txt": contents } }, "played": { "<App>": time } }`, with every `oldjava.saves.<App>` store (`<App>.then` included) and the passport's stamps.
- Send to my phone shows a QR code (and the link with Copy link) of the home page with `?saves=` and the bundle, deflated (`CompressionStream('deflate-raw')`) and base64url encoded. `qr.js` makes the code with no library: byte mode, error correction level L, versions 1 to 40, laid out the way Project Nayuki's QR Code generator does it. Its codes were checked by decoding them with jsQR at lengths from 1 to 2,950 characters (versions 1 to 40), and the code drawn on the page was checked module by module against the encoder. A link that needs a code above version 30 (longer than 1,732 characters) is too dense to scan from a screen, so the panel offers Copy link and Download instead. A page served from `localhost` or `127.0.0.1` says that a phone can only open the link if it can reach that address.
- Download saves the bundle as `oldjava-saves.json`, and Load reads one (from Download, or from the desktop launcher's Saves, see [Launcher](../Launcher/README.md)).
- Opening a link or loading a file changes nothing by itself. A dialog lists each app in it, with the record it brings and the one here now ("Already the same here" for an app whose files match), each with a box (ticked where they differ), and the passport stamps not collected here. Bring them in writes the ticked apps' files over the same files here (other files of the app are kept) and adds the stamps. The link's `?saves=` is taken off the address at once, so a reload does not offer it again.
- The player's app keeps its own copy of its files and writes them back when it closes, so before anything is written the player's frame is emptied (`about:blank`), then the app is started again on what was brought in.
- `saves.js` and `qr.js` load on the home page only, and are part of Save all for offline.
- Files in a bundle are checked: store names must be app names, paths must be absolute and not under `/Downloads/`, and contents strings of bytes (one character each, as `web.rt.Saves` keeps them).

## Install and offline

The site is a progressive web app: it can be installed as an app with its own window and icon, and every app can be kept on the device to play with no connection.

- `boot.js` links `manifest.webmanifest`, the icon (`icons/icon.svg`, plus PNG renders of it) and the theme color on every page, and registers the service worker `sw.js`. The manifest opens the home page in a standalone window and has shortcuts to Minesweeper, Flappy Bird, NathaNOS and Synthesizer Keyboard (`index.html#<App>`).
- `sw.js` is network first: every request goes to the server as before, so a new build shows up on the next load, and each good answer is also kept in the `oldjava-v1` cache. When the network fails, the cached copy answers. Cache keys leave out the query string, so the player's `<App>/index.html?embed` and the app's own page share one entry. A page that is not cached gets a short "You are offline" page with a link home.
- The home page's Take the arcade with you panel (the Take it with you tab of Your arcade) has Install app (the browser's own install prompt, which `boot.js` keeps for this button; where the browser offers none, a note points at its menu) and Save all for offline. Saving reads each app's file list from its page (`index.html`, `classes.js` and the `data-files`), adds the home page, `boot.js`, `qr.js`, `saves.js`, `news.js`, `clockbar.js`, `history.txt`, `shim.css`, the manifest, icons and thumbnails, and fetches them four at a time into the cache with a progress bar, then reports the size (9.1 MB before Bible Downloader joined; its page adds about 0.45 MB). Apps played once are kept too, so the panel also says how many are saved already.
- A gallery card whose files are all cached carries an Offline chip. When the browser reports no connection, a banner under the title says how many saved apps still play, and the cards of the others fade out and say Needs a connection.
- Service workers need a secure context: `localhost`, `127.0.0.1` or HTTPS. Elsewhere the panel stays hidden and the site works as before.
- The icons in `icons/` are PNG renders of `icons/icon.svg` (192 and 512 px, a 512 px maskable one with the art inside the safe zone, and a 180 px `apple-touch-icon.png`). To change the icon, edit the SVG and render the PNGs again, for example with headless Chrome (`--screenshot` with a matching `--window-size`).

## Sound

The site's own controls and moments make short sounds, synthesized with the Web Audio API in `boot.js` (`window.oldjavaSound`), so no sound file is downloaded. The apps keep their own sound and get none of these.

- Each skin has its own voice: soft bell tones (a sine with a quiet partial two octaves up) in Modern, a filtered square-wave beep like a PC speaker in Classic, and chiptune blips that drop onto their note from a fifth above in Arcade.
- Sounds: a tap for any button or link of the site (not the app's windows or the touch controller, whose presses belong to the app), a rising arpeggio when an app is swapped into the home page's player or an app page starts, open and close notes for the Switch app panel, a jingle in the new skin's voice when the skin changes, a stamp knock and two notes for a new passport stamp (a longer fanfare for the last), a falling line when an app exits, and a chime when Save all for offline finishes (a low two-note warning when it fails or the connection drops).
- Clock's moments, heard on any page while Clock is not open (see Clock follows you): a falling line when a focus session ends, a rising one when a break ends, and a five-note bell when the timer runs out.
- Arcade has two of its own: a new app powers on with a low thump and a rising whine, timed with the skin's power-on animation, then two notes; a stamp sounds like a coin (B5 then a held E6).
- Each tune is a list of semitones above the voice's root note (`TUNES` and `ARCADE_TUNES` in `boot.js`), so a voice and a tune can be changed separately.
- The Sound button in the toolbar (a note, with the word on pages 1000 px wide or more) mutes or unmutes them. The choice is remembered in `localStorage` (`oldjava.sound`) and reaches every open page of the site through the `storage` event.
- Browsers start audio only after a click or key press, so nothing plays before the visitor's first one on that page. An app page plays its start sound when the visitor presses Play on its title screen; the home page's player plays it on every swap.

## Clock follows you

Clock's timer, stopwatch and focus sessions count against the wall clock and are saved as they change (see [Clock](../Clock/README.md)), but before this a focus session only did its job while the Clock page was in front: start 25 minutes of focus, open a game for the break, and nothing on the game's page said how long the break had left or when it was over. Now the clock follows the visitor round the site, and a break is an invitation into the arcade.

- While a timer, stopwatch or focus session runs, every page's toolbar (the app pages' band and the home page's floating bar) shows a chip for each: a ring that drains, red for focus, green for a break, blue for the timer, violet for the stopwatch (once round a minute), and the time left ("Break 3:10"). Below 1000 px wide only the ring and the time show. The last ten seconds blink (not with reduced motion). Its tooltip and accessible name say which session it is and when it ends. Clicking it opens Clock, past its title screen.
- When a focus session ends, the page rings the break phrase (a falling line in the skin's voice, see Sound) and says so: "Focus 2 of 4 done: break time. 5 minutes until 3:47 pm. Spend it on FlappyBird? The clock keeps time and calls you back.", with a Play button. The game is a quick one (FlappyBird, DinoGame, Minesweeper, NumberGuess or SpriteFloatyStars), one the passport has not stamped yet when there is one. On a game's page it says "Play on" instead. The Clock page offers the game too, under Clock's own bell.
- When the break ends, a rising phrase and "Break's over. Focus session 3 of 4 is ready to start." with Back to focus, which opens Clock past its title screen. When the timer runs out, the timer's bell and "Your 5-minute timer rang at 3:42 pm." with Open Clock.
- On an app page the news shows in the toolbar band's news line (see App pages), tagged Break, Focus or Timer in the moment's color, for 15 seconds; on the home page as a toast, whose buttons swap the game (or Clock) into the player.
- `clockbar.js` does this. `boot.js` adds it to a page (not to the home page's player or other embedded pages) only once Clock's saved file (`oldjava.saves.Clock`, see Saved files) has a running timer, stopwatch or session, or as soon as one starts in another tab (the `storage` event). It reads the file once a second and plays the sessions forward the way `Focus.java` does, but never writes it: Clock catches up on what happened, and logs the minutes, when it opens again.
- Each moment rings once, whichever pages are open: the page that rings it first keeps its time in `oldjava.clockBell`. None rings while Clock itself runs on some page (it rings for itself): the Clock page, or the home page's player showing Clock, keeps `oldjava.clockOpen` up to date every 5 seconds while it runs and removes it when the page goes. A moment more than a minute old is not news (Clock's own rule for what happened while it was closed). A hidden tab tells the moment when it is looked at again. Browsers slow the timers of tabs hidden for a while to once a minute, so a bell from such a tab can be up to a minute late.

## Between pages

Going from one page of the site to another (Next, Switch app, an exit screen suggestion, Full page, All apps, Then | Now) used to drop the visitor on a blank page that then built itself. Now the pages hand over to each other with the browser's cross-document view transitions, so the arcade moves like one machine:

- `shim.css` opts every page in (`@view-transition { navigation: auto; }`), except when the system asks for reduced motion. The app pages' toolbar band is its own layer (`view-transition-name: oldjava-band`), so it stays put while the stage under it changes.
- A clicked thumbnail (a Switch app card or an exit screen suggestion) grows into the next app's title card. Full page in the home page's player grows the player's screen into the app's title card, and All apps shrinks the app's stage (its title card, or its desktop once it runs) back into the player. Next and Previous (the toolbar's Next link, a controller's LB / RB) slide the stage sideways, and Then | Now fade through sepia.
- In Classic the trips take about half as long. In Arcade every trip is a CRT changing channel: the old picture collapses into a bright line and goes dark, and the new one opens out of it, while the band stays lit.
- The trip code is at the end of `boot.js`: on `pageswap` the old page works out the kind of trip from the two addresses (and the gallery order), names the clicked thumbnail or its stage `oldjava-hero`, and leaves the kind in `sessionStorage` (`oldjava.trip`); on `pagereveal` the new page adds it as a view transition type and names its own title card or player screen. The home page holds its first frame until the player is parsed (`<link rel="expect" href="#player-frame" blocking="render">`). Pages in the player (`?embed`) and the screen saver skip their own transitions.
- Browsers without cross-document view transitions (Chrome and Edge 126 and later have them) change pages as before. Tested in Chrome by pausing the transitions' animations part way and checking which layers each trip made.

## Find

Ctrl+K (Cmd+K on a Mac) on any page, / on the home page, the toolbar's Find button or the search bar above the gallery opens one box for the whole site. Before it, reaching an app meant scrolling the gallery or opening Switch app, and most of the site's features (skins, replay, source, records, the passport, the Then versions, watching the computer play) sat behind their own buttons on some pages and not others.

- It finds apps by name, hint or category (letters in order work for names: "msw" finds Minesweeper), each app's Then version ("Flappy Bird: as it was") and, for the four games in `WATCH`, watching the computer play. On the home page an app opens in the player, as the gallery's Play does (Shift+Enter opens its own page); elsewhere it opens the app's page.
- It finds things to do on the current page by clicking the page's own controls: How to play, Read the source, Share, Instant replay, Fit or Actual size, Pop out, the controller, Switch app and All apps on an app page; Shuffle, Big screen, Restart and the Your arcade tabs on the home page; and anywhere the other two skins, site sounds and Surprise me (an app not played yet). Controls a page does not show are left out.
- It finds every Java source file of every app, read from each app's `source/files.txt` the first time something is typed, and opens it in that app's Source panel (`#source:<path>`), on this page if it is that app's.
- With nothing typed it offers the apps played last (`oldjava.lastPlayed`), some not played yet, and the page's things to do. Arrow keys move, Enter opens, Esc or the same shortcut closes; keys typed in the box never reach the app.
- The code is `find.js`, which `boot.js` adds the first time the box opens (the end of `boot.js` has the shortcut, the toolbar button and what it lends through `window.oldjavaSite`). In the home page's player the shortcut is passed up to the home page, so the box opens over the whole page. The box keeps the focus while it is open, since the player focuses its iframe when it loads the next demo game. Off in the thumbnail, clip and screen saver modes. `find.js` is in the offline file list.

## The story

`story.html` tells [HISTORY.md](../HISTORY.md) on the site, in four chapters, with the things each chapter talks about beside the words. A link under the home page's intro and a "The story" entry in Find lead to it. Before it, a visitor met 20 apps with no word on where they came from, and the history lived only in the repo.

- **The originals**: the 2016 quotes Stock Checker saved, read from `StockChecker/stockCheck.csv` (its five real quotes, and a note for the 95 empty rows after them), and all 20 apps grouped by where each was recovered from, linking to their pages.

## Instant open

Every app page used to load from scratch after its link was clicked: the page, `boot.js`, the app's program (`classes.js`, 57 KB to 1.4 MB) and its files, then the title screen's boot log ran up to Ready. Now the next page is made ready while the visitor is still choosing it, so the click only swaps it in.

- In Chrome and Edge, `boot.js` adds speculation rules to the home page and every app page: a link to an app page (`<App>/index.html` or `then.html`), the home page or the story page is prerendered when the pointer rests on it for about 200 ms or presses it (`eagerness: "moderate"`). That covers Switch app, Next, the exit screen's suggestions, a gallery card's Full page, All apps and Then | Now. The prerendered page loads its program and files and shows its title screen with Play lit; the app itself still starts only on Play. Once opened, its boot log adds "Loaded ahead, while you chose it" (with "no wait", or the head start it had if it was not quite ready). The page transition (Between pages) plays as before.
- Find's highlighted result is made ready too (`window.oldjavaSite.ready`, called by `find.js`): a list rule of its own for that one page, replaced as the highlight moves, so Enter opens it at once.
- The home page's player is an iframe, which cannot be prerendered, so pointing at a rail button, a gallery card's Play or its picture (or highlighting an app in Find on the home page) fetches that app's page, program and `data-files` into the browser's cache instead ("warm"). Browsers without speculation rules warm every app link the same way.
- Left out: links to `?embed` and `?watch` pages (a watched game starts playing at once), links that open a new tab or download, and the page's own address. Nothing is fetched ahead with Save-Data on or on a 2G connection, nor in the player, thumbnail, clip and screen saver modes.
- Chrome throws a prerendered page away when it calls `navigator.getGamepads()`, which the screen saver's idle clock polls every second, so while a page is prerendering `boot.js` answers that call with no controllers.
- A page that is never opened leaves no trace: until it is opened (`prerenderingchange`), `boot.js` holds back whatever reaches beyond the page (`whenShown`). An app that would start without a title screen (Run again, the Clock chip's link, the home page's player) waits, and with it its sounds, saves, replay recording and Clock's "open here" beat; `clockbar.js` waits too, so an unseen page cannot take Clock's bell from the one in view. Passport stamps and `oldjava.lastPlayed` already wait for the visitor's first click or key, and the screen saver's idle clock does not run on a page that is not visible. A link that skips the title screen (the Clock chip) is read again on opening, so a prerendered Clock page skips it too.
- Tested in a plain Chrome window (DevTools turns prerendering off, so not over the DevTools protocol): the server log showed the next page requested when the rule fired and not again when it was opened, and the opened page's boot log had the new line with Play already lit, for an app page, a `then.html`, the home page and a Find result. Hover timing itself is Chrome's.

## Side by side

These were desktop programs, and a desktop runs more than one at a time. The Side by side button (◫) in an app page's toolbar opens a picker of a second app to run beside this one: "Good together" first (Clock, for a focus session, timer or stopwatch beside anything; ScreenSaver, for something to watch; MusicTheoryExpert and SynthesizerKeyboard for each other), then every other app.

- The second app runs in a panel on the right of the stage: its page in an iframe with `?embed`, as in the home page's player, so it starts at once, keeps its own saves and fits its windows to the panel. The stage (and the title screen, overlays, the pretend Windows layer and a popped out card) ends at the panel's edge (`--dock-w`), so neither app covers the other.
- The panel's head names the app and has Swap (this app becomes the main one, on its own page with no title screen, and the one that was main goes beside it), Change (the picker again), Full page and close. "Keys here" lights while the panel has the focus; a click in either app gives it the keys.
- Its left edge drags (or takes Left and Right arrow keys) to share the page, from 15% to 75% of its width, with at least 320 px for the panel and 420 px for the stage.
- `oldjava.dock` (localStorage) keeps the app and the width, so the panel opens again on every app page until it is closed. It does not open beside itself (the page of the docked app shows no panel) and, as an effect beyond the page, waits until a prerendered page is opened (`whenShown`).
- What the docked app asks of the page around it (an exit screen's suggestions, Find, Share, Replay, Your skin) the page answers as the home page does for its player: a suggestion opens in the panel, and the rest open over the whole page.
- Wide pages only: below 901 px the button and the panel are not shown (the setting is kept for a wider window). Find lists it as "Side by side" where it is offered.

Find, Ctrl+K: keys typed right after the first Ctrl+K of a page, while `find.js` is still loading, used to reach the app behind the box (a title screen would start the app on them). They are now held and typed into the box once it has the focus, also from the home page's player and the panel beside. Keys typed in the open box no longer start the app behind it either: the title screen's any-key start now leaves keys in the box (`.shim-find`) alone, as it does for the toolbar and the other panels.

## Limitations

- Only the AWT/Swing API these apps use is implemented. A new app, or a change that calls something missing, fails the build with "Method ... was not found".
- Windows cannot be resized by dragging their edges, and there are no minimize or maximize buttons.
- `Robot` cannot see or control anything outside the page. The Windows key and the shortcuts made with it go to the page's pretend Windows, which knows only the Windows key alone and Win+E.
- Game controllers were tested with simulated ones (a page script standing in for `navigator.getGamepads`), not a physical controller. A browser may not count a controller button as the click or key press it waits for before a page may play sound, so an app's first sounds may need a click or key.
- Pop out needs the browser's Document Picture-in-Picture API; where it is missing the button is not shown. It was tested in Chrome on Windows by dispatching mouse and key events into the small window from a script, since the browser automation used could not click inside it.
- What an app saves is kept only in that browser, and only in `localStorage` (about 5 MB per site), until Your records carries it to another browser or the desktop. Saving for offline keeps the apps' files; their saves are already local.
- Bringing saves in replaces an app's files whole: Minesweeper's file from another device replaces the one here, best times and all, so a better time kept only here is lost if that app is ticked (the dialog shows both records first). An app running in another tab of the site keeps its old copy and writes it back the next time it saves; the home page's own player is restarted. The QR code was checked with a decoder, not scanned with a real phone.
